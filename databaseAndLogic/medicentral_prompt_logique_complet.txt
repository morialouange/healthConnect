CONTEXTE ET LOGIQUE METIER
=============================================================

MediCentral est une plateforme SaaS médicale qui relie
plusieurs hôpitaux en réseau. Chaque hôpital utilise la
même application mais voit uniquement ses propres données
opérationnelles (médecins, rendez-vous, services).
Le dossier médical du patient est GLOBAL : il est visible
par tous les hôpitaux du réseau quand le patient se présente.

REGLE D'ISOLATION :
- Données privées (rendez-vous, médecins, services,
  créneaux, disponibilités) :
  filtrées par id_etablissement — chaque hôpital voit
  uniquement les siennes
- Dossier médical : GLOBAL — accessible par tout médecin
  du réseau quand le patient lui donne son numéro patient

=============================================================
ROLES DU SYSTEME (4 rôles — exigence doc : minimum 3)
=============================================================

1. SUPER_ADMIN
   - Ajoute et gère les hôpitaux du réseau
   - Crée les comptes ADMIN de chaque hôpital
   - Voit les statistiques globales du réseau
   - Accède aux journaux d'accès aux dossiers
   - Consulte l'historique des modifications du dossier

2. ADMIN (un par hôpital)
   - Crée les comptes des MEDECINS de son hôpital
   - Modifie les informations d'un médecin de son hôpital  [NOUVEAU L23]
   - Voit les détails complets d'un médecin               [NOUVEAU L23]
   - Supprime (désactive) un médecin de son hôpital       [NOUVEAU L23]
   - Gère les services de son hôpital (CRUD complet)      [NOUVEAU L24]
   - Voit les statistiques de son hôpital
   - Génère les rapports mensuels de son hôpital
   NOTE : L'admin NE gère PAS les rendez-vous.
          C'est le MEDECIN qui confirme, refuse et clôture.

3. MEDECIN
   - Complète son profil une seule fois après le 1er login
     (données de la table medecins)
   - Modifie son propre profil à tout moment              [NOUVEAU L25]
   - Déclare ses disponibilités par semaine (L14)
   - Confirme ou refuse les RDV des patients (L02)
   - Marque un RDV comme TERMINE (L02)
   - Accède au dossier médical global d'un patient
   - Peut voir ET modifier le dossier (notes, diagnostic)
   - Crée des consultations pour les patients
   - Rédige des ordonnances multi-lignes
   - Réfère un patient vers un autre hôpital

4. PATIENT
   - Crée lui-même son compte (table utilisateurs uniquement)
   - Complète son profil une seule fois après le 1er login
     (données de la table patients)
   - Modifie son propre profil à tout moment              [NOUVEAU L25]
   - Après profil complété : accède à son dashboard
   - Peut voir son dossier médical (lecture seule)
   - Prend RDV uniquement sur créneaux libres (L14)
   - Voit ses ordonnances et référencements (lecture seule)
   - Annule ses propres RDV si statut = RDV_DEMANDE

LOGIQUE 01 — GENERATION AUTOMATIQUE DES NUMEROS
-------------------------------------------------------------

Description :
  Quand un patient complète son profil pour la première
  fois, le système génère automatiquement deux identifiants
  uniques sans intervention humaine.

  numero_patient : PAT-AAAA-NNNNN  ex: PAT-2026-00042
  numero_dossier : DOS-AAAA-NNNNN  ex: DOS-2026-00042

Comment ça fonctionne :
  - AuthService calcule le prochain numéro en comptant
    les patients existants dans la base
  - Les deux numéros sont générés dans la même transaction
  - Ils ne changent jamais même si le patient change
    d'hôpital ou met à jour ses informations

Tables concernées : patients, dossier_medicals
EJB concerné      : AuthService — completerProfilPatient()

LOGIQUE 23 — CRUD COMPLET DES MEDECINS PAR L'ADMIN    [NOUVEAU]
-------------------------------------------------------------

Description :
  L'ADMIN peut gérer entièrement les médecins de son hôpital :
  créer (déjà existant L12), modifier leurs informations,
  voir leurs détails complets, et les désactiver (suppression
  logique). Aucune suppression physique en base pour préserver
  l'historique médical.

Actions disponibles pour l'ADMIN :
  1. CREER     : déjà couvert par L12
  2. MODIFIER  : modifier spécialité, expérience, numero_ordre
                 et informations utilisateur (full_name, email)
  3. VOIR      : fiche détail complète d'un médecin
  4. DESACTIVER: suppression logique — actif = false
                 Le médecin ne peut plus se connecter.
                 Ses données historiques sont conservées.

Règles de sécurité :
  - L'ADMIN ne peut gérer QUE les médecins de son hôpital
    (filtre obligatoire sur id_etablissement)
  - Un médecin avec des RDV RDV_CONFIRME en cours ne peut
    pas être désactivé → message d'erreur JSP
  - Seul un compte avec rôle MEDECIN est concerné

Comment ça fonctionne — MODIFIER :
  - AdminServlet reçoit GET /admin/medecins/modifier?id=5
    → charge le médecin + son utilisateur
    → forward vers admin/medecin-modifier.jsp
    → formulaire pré-rempli avec ${medecin} et ${utilisateur}
  - AdminServlet reçoit POST /admin/medecins/modifier
    → Validation manuelle (L22) : full_name, email, specialite,
      experience (numérique), numero_ordre (numérique)
    → MedecinService.modifierMedecin(id, dto)
      * Vérifie que id_etablissement correspond (L11)
      * Modifie Utilisateur.full_name, Utilisateur.email
      * Modifie Medecin.specialite, experience, numero_ordre
      * Flush + commit JPA
    → Redirection vers /admin/medecins avec message succès

Comment ça fonctionne — VOIR DETAILS :
  - AdminServlet reçoit GET /admin/medecins/detail?id=5
    → MedecinService.getMedecinDetail(id, idEtablissement)
      * Charge Medecin + Utilisateur associé
      * Charge nombre de RDV totaux (JPQL COUNT)
      * Charge consultations du mois (JPQL COUNT)
      * Charge prochains RDV (5 prochains)
      * Charge statut des congés en cours
    → forward vers admin/medecin-detail.jsp
    → JSP affiche :
        - Informations personnelles (full_name, email)
        - Informations médicales (spécialité, expérience)
        - Statistiques d'activité (RDV totaux, ce mois)
        - Liste des 5 prochains RDV
        - État des congés
        - Boutons : Modifier | Désactiver

Comment ça fonctionne — DESACTIVER :
  - AdminServlet reçoit POST /admin/medecins/desactiver?id=5
    → MedecinService.desactiverMedecin(id, idEtablissement)
      * Vérifie L11 : id_etablissement correspond
      * Vérifie qu'il n'y a pas de RDV_CONFIRME en cours
        JPQL : SELECT COUNT(r) FROM RendezVous r
               WHERE r.medecin.id = :id
               AND r.statut = 'RDV_CONFIRME'
               AND r.dateRendez >= CURRENT_DATE
        Si > 0 → AccesInterditException avec message métier
      * Utilisateur.actif = false
      * EtabliUtilisateur.actif = false
    → Redirection vers /admin/medecins
    → Notification NotificationService au médecin concerné

Tables concernées : medecins, utilisateurs,
                    etabli_utilisateurs, rendez_vous
EJB concerné      : MedecinService (nouveau EJB)
                    - getMedecinsByEtablissement()     [existant]

LOGIQUE 25 — MODIFICATION DU PROPRE PROFIL              [NOUVEAU]
-------------------------------------------------------------

Description :
  Chaque utilisateur peut modifier son propre profil à tout
  moment depuis son dashboard. Chaque rôle peut modifier
  ses champs spécifiques. Un utilisateur ne peut JAMAIS
  modifier le profil d'un autre utilisateur.

  PATIENT peut modifier :
    - Informations personnelles : full_name, telephone, adresse
    - Informations médicales    : allergies, groupe_sanguin
    - Mot de passe              : avec vérification ancien MDP

  MEDECIN peut modifier :
    - Informations personnelles : full_name, telephone (via utilisateur)
    - Informations médicales    : specialite, experience
    - Mot de passe              : avec vérification ancien MDP
    NOTE : Le médecin NE modifie PAS son numero_ordre
           (seul l'admin peut le faire via L23)

  ADMIN peut modifier :
    - Informations personnelles : full_name, email
    - Mot de passe              : avec vérification ancien MDP

  SUPER_ADMIN peut modifier :
    - Informations personnelles : full_name, email
    - Mot de passe              : avec vérification ancien MDP

Règle importante :
  - La session id_utilisateur sert de clé de sécurité
  - Le Servlet lit UNIQUEMENT l'id depuis la session
  - Il est INTERDIT de passer id_utilisateur en paramètre
    de formulaire (risque de modifier le profil d'un autre)
  - Validation manuelle obligatoire (L22)

Comment ça fonctionne :

  AFFICHAGE DU FORMULAIRE :
  - Chaque dashboard a un lien "Mon Profil" ou icône user
  - ProfilServlet GET /profil/mon-profil
    → Lit id_utilisateur depuis HttpSession (jamais paramètre)
    → ProfilService.getMonProfil(idUtilisateur, role)
      * PATIENT : charge Utilisateur + Patient
      * MEDECIN : charge Utilisateur + Medecin
      * ADMIN   : charge Utilisateur
    → forward vers profil/mon-profil.jsp
    → JSP affiche formulaire pré-rempli avec ${utilisateur}
      et ${profilSpecifique} selon c:choose sur ${role}

  SOUMISSION DES MODIFICATIONS :
  - ProfilServlet POST /profil/mon-profil
    → Lit id_utilisateur depuis session (JAMAIS param POST)
    → Validation manuelle (L22) selon le rôle :
        full_name  : non vide, max 100 chars
        telephone  : numérique, 8-15 chiffres
        allergies  : texte libre, max 500 chars
        specialite : non vide si MEDECIN
        experience : numérique >= 0 si MEDECIN
    → ProfilService.modifierMonProfil(idUtilisateur, role, dto)
      * Charge l'entité depuis la base avec idUtilisateur
      * Vérifie que l'entité appartient bien à cet utilisateur
      * Modifie uniquement les champs autorisés pour ce rôle
      * Flush + commit JPA
    → Redirection vers dashboard du rôle avec message succès

  CHANGEMENT DE MOT DE PASSE (tous rôles) :
  - Formulaire séparé sur la même page (section dédiée)
  - ProfilServlet POST /profil/changer-mot-de-passe
    → Lit id_utilisateur depuis session
    → Paramètres : ancien_mdp, nouveau_mdp, confirmation_mdp
    → Validation manuelle :
        * ancien_mdp correspond au hash en base
        * nouveau_mdp >= 8 caractères
        * nouveau_mdp == confirmation_mdp
    → ProfilService.changerMotDePasse(id, ancienMdp, nouveauMdp)
      * Vérifie BCrypt/SHA-256 de ancien_mdp vs hash en base
      * Si OK → hash nouveau_mdp → Utilisateur.password_hash
      * Si NOK → message d'erreur JSP
    → Redirection vers /profil/mon-profil

Tables concernées : utilisateurs, patients, medecins
EJB concerné      : ProfilService (nouveau EJB)
                    - getMonProfil(idUtilisateur, role)
                    - modifierMonProfil(idUtilisateur, role, dto)
                    - changerMotDePasse(id, ancien, nouveau)
Servlet concerné  : ProfilServlet — étendu
                    GET  /profil/mon-profil
                    POST /profil/mon-profil
                    POST /profil/changer-mot-de-passe
